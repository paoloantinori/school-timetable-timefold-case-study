# Benchmark mechanism audit — TASK-386 (2026-07-21)

## Verdict

The offline Timefold benchmarker (`PlannerBenchmarkFactory` + `solverBenchmarkConfig*.xml`) is **not usable, as-is, as an honest stand-in for the current 6-phase pipeline**. Two independent, mechanically-confirmed gaps compound:

1. **No input file exists.** `local/data/schedule-production.json` (the file every existing config's `<inputSolutionFile>` points at) is not present anywhere in the repo or `local/`. It has to be hand-produced via a live app cycle (pre-assign/solve, then `GET /api/schedule/export`) before any benchmark run can even start.
2. **Even with a fresh export, the statics the current pipeline depends on are not fully rebuilt.** `SchoolScheduleSolutionFileIO.read()` (the benchmarker's `solutionFileIOClass`) populates 7 of the 10 statics `ScheduleService.refreshSolverStatics()` populates in production. The three it never touches — `GroupCalendarRule`, `DailyActivityQuota`-derived maps, and the MRV `lessonAvailableTimeslotCounts` — are read by `DayClusteredConstructionPhase` (phase 1) and by the H20/M18/M20 constraints. One of the three (`GroupCalendarRule`) cannot be fixed by touching `SolutionFileIO` at all: it is not a field on the `SchoolSchedule` solution class, so it never round-trips through the exported JSON in the first place.

None of these gaps crash the benchmark outright — every missing static has a graceful "backward compatible / fully open" default (confirmed by reading the fallback code, not assumed). The failure mode is silent optimism bias: groups with real 2026/27 calendar restrictions (TASK-342 seed) get treated as calendar-unrestricted, and phase 1's MRV-based difficulty ordering degrades to a coarser tiebreak. This means a benchmark run through this mechanism would not be comparable to the live runs (12-16) the task is trying to beat, even though the bias affects every arm identically (a same-suite relative ranking of phase-2 knobs might still be internally consistent — the absolute numbers would not be).

The 12 existing `solverBenchmarkConfig*.xml` files are additionally, and separately, architecturally stale: they use a generic `FIRST_FIT` `<constructionHeuristic>` plus ONE combined `<localSearch>` mixing timeslot+room moves per arm — nothing like the current pipeline's custom `DayClusteredConstructionPhase` → `PhaseTransitionMarker` → compactness LS → `PhaseTransitionMarker` → RuinRecreate LS → `PhaseTransitionMarker` → room CH → `PhaseTransitionMarker` → room LS shape. They predate both TASK-377 (H1/H2/H3/H16a were inert during timeslot phases — fixed by switching to `forEachIncludingUnassigned`) and TASK-378 (the fallback CH was deleted; `DayClusteredConstructionPhase` + markers replaced it). Running any of them today would benchmark a different, easier problem than the one runs 12-16 solved.

**Recommendation (adopted): use the sequential live A/B protocol** (`scripts/benchmark/run-honest-ab.sh`) instead of fixing the offline mechanism. Fixing it properly means: (a) writing an export/import cycle to regenerate the input file, (b) extending `SchoolScheduleSolutionFileIO` to call the three missing static setters, and (c) either adding `GroupCalendarRule` as a `@ProblemFactCollectionProperty` on `SchoolSchedule` (a production domain change needing its own review) or permanently accepting "calendar always open" in any offline benchmark. That is a materially bigger, riskier change than the live A/B protocol, which reuses the exact code path (`ScheduleService.loadSchedule(true)`, full statics, full pipeline) that runs 12-16 already validated.

### (d) Timefold 2.3 community-edition benchmarker limitations (warm-up, parallel benchmarks, custom phases)

Verified via `WebSearch` against `docs.timefold.ai` (this session; not asserted from training memory) — no community-edition restriction blocks this project's use case:

- The benchmarker module (`timefold-solver-benchmark`) is part of the open-source Apache-2.0 core, not an Enterprise-only add-on.
- `parallelBenchmarkCount` supports `AUTO` (Timefold decides the count) or a fixed number; a custom `ThreadFactory` can be plugged in for constrained environments. Confirmed present in `benchmark.xsd` (`<xs:element minOccurs="0" name="parallelBenchmarkCount" type="xs:string"/>`, `warmUpSecondsSpentLimit`/`warmUpMillisecondsSpentLimit`/etc., all present as direct children of `plannerBenchmarkConfig`).
- Warm-up is configurable per the standard `warmUp*SpentLimit` elements and can be disabled by setting `warmUpSecondsSpentLimit` to 0.
- Custom phases ARE supported inside a benchmark's `<solver>`: `benchmark.xsd`'s `solverConfig` complex type includes `customPhase` in the same phase choice group (`constructionHeuristic | customPhase | exhaustiveSearch | localSearch | partitionedSearch`) as `solver.xsd`'s own `solverConfig` type — confirmed by extracting both XSDs from the `2.3.0` JARs and diffing the phase-choice block. Custom phase parameters can even be exposed to the benchmarker via `customProperties` for tuning.
- Practical caveat unrelated to this project's scale: move-thread-based multithreading (a different feature from `parallelBenchmarkCount`) has diminishing returns above ~4-8 threads at high move-evaluation speeds — not relevant here since `solverConfig.xml` doesn't configure `moveThreadCount`.
- Net: the XSD/API fully supports the current custom-phase pipeline inside a benchmark config. **The break is entirely in this project's own `SolutionFileIO`/export-shape gap, not a Timefold platform limitation.**

### XSD validation tooling gap (relevant to `.claude/rules/benchmark-xsd-validation.md`)

`scripts/validate/validate-solver-xml.sh` extracts only `solver.xsd` from `timefold-solver-core` (`validate-solver-xml.sh:23-25`) and validates against files with a `<solver>` root. Running it against any `<plannerBenchmark>`-rooted file fails immediately with `No matching global declaration available for the validation root` — reproduced directly against the existing (already-committed) `solverBenchmarkConfig.xml`:

```
$ bash scripts/validate/validate-solver-xml.sh src/main/resources/solverBenchmarkConfig.xml
src/main/resources/solverBenchmarkConfig.xml:2: element plannerBenchmark: Schemas validity error :
Element '{https://timefold.ai/xsd/benchmark}plannerBenchmark': No matching global declaration available for the validation root.
```

This is not a defect introduced by this task — it's a pre-existing gap in the wrapper script (it was written for `solverConfig.xml`/`preAssignmentPhase*.xml`, all of which are `<solver>`-rooted). `benchmark.xsd` (self-contained, extracted from `timefold-solver-benchmark-2.3.0.jar`, does not `import`/`include` `solver.xsd` — it redeclares an equivalent `tns:solverConfig` type in its own `https://timefold.ai/xsd/benchmark` namespace) is the correct schema for `<plannerBenchmark>` files and was used directly via `xmllint --schema benchmark.xsd <file> --noout` for this task's `solverBenchmarkConfig-2026-honest.xml`. The per-arm `local/benchmark-arms/solverConfig-arm-*.xml` files ARE `<solver>`-rooted and validate correctly through the existing wrapper script unchanged.

## Recommended execution order (given ~90 min/live run)

1. **Arm A (control)** — must still be run even though its knobs match today's live config, because its phase-2 budget here is pinned to 3600s (not run 16's 5400s experiment), making it the correct baseline for comparing against runs 12-15.
2. **Arm E (tabu 11)** — cheapest structural variant of the control (same move mix/forager, only tabu memory length differs).
3. **Arm C (acceptedCountLimit 500)** then **Arm D (acceptedCountLimit 2000)** — read together to bracket the control's forager-width sensitivity in one pass.
4. **Arm F (pillar moves removed)** — run after the tabu/forager sweep so any change is attributable to move mix, not confounded with an already-tested acceptor/forager variant.
5. **Arm B (late acceptance 400)** — most different acceptor family; benefits from having the tabu-family sweep (A/C/D/E) as an interpretive baseline.

Total: 6 × ~90 min ≈ 9 hours wall clock if run back-to-back; the single-DB-actor rule means these must run strictly sequentially, never concurrently, and never while another solve is active.
