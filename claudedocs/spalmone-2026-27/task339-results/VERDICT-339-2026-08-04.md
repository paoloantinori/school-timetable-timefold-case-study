## Domanda

Le lezioni PINNATE (pre-assegnate authoritative + mid-solve promoted) causano violazioni hard nel run
finale? Se si', il pinning introduce infeasibility che il solver non puo' toccare (le pinnate sono
fixed), e questo spiegherebbe residui hard che non si chiudono (H17/H29). Predizione ex-ante: le
pinnate dovrebbero essere 0-violanti per costruzione (canPin() le valida), con il rischio aperto che i
PROMOTED pin sfuggano al gate.

## Metodo

Script `scripts/analyze/pinned-hard-impact.py`: legge l'`export.json.gz` di un run (lezioni con
`pinned` + `promotedPin` + timeslot + room + teacher.pseudo + group), ricomputa i vincoli hard che
possono essere "pin-caused" e per ciascuno riporta il coinvolgimento di lezioni pinnate:
- H29 room-null (filtro esatto replicato dal Java: timeslot!=null && room==null && !pinned &&
  !teacher.pseudo -> le pinnate sono ESENTI per costruzione).
- H1 teacher-conflict / H3 group-conflict (cluster >1 lezione stessa (teacher/group, date, slot)).
- H17 vertically-compact (gap "buco interno" tra primo e ultimo slot occupato del giorno del gruppo;
  scored salta i gap con ENTRAMBI i flank pinnati = break-level pinned-exempt).

**VALIDAZIONE:** i conteggi H17/H29 ricomputati combaciano ESATTAMENTE con lo score reale dei run su
5 run misurati (il che valida la logica di ricomputazione). H0 (unassigned), H2 (room conflict con
esenzione co-presenza) e H7 sono fuori scope (H0 e' unpinned-by-nature; H2 e' 0 sui run misurati).

## Verdetto

**Sui 5 run misurati, le lezioni PINNATE causano ZERO violazioni hard.** (Scope: analysis.json
conferma che sui 5 run le uniche hard che fireano sono H17 e H29; H1/H2/H3/H7/H11 = 0 hard. Le
pinnate causano 0 delle H17/H29.) canPin() funziona sulle pinnate authoritative; i residui sono
INTERAMENTE unpinned-driven:
- H17 = gap tra lezioni unpinned che la LS non ha compattato (search-side, non pin).
- H29 = lezioni unpinned che la fase room ha lasciato room-null (room-phase failure, non pin).

**Caveat strutturale (H2/H7/H11):** questi vincoli NON hanno filtro `!pinned` nel solver, quindi una
pinnata PUO' parteciparvi su un run ipotetico in cui fireassero. Ma sui 5 run fireano 0 hard
(analysis.json), quindi le pinnate non vi causano hard qui. La verifica "pinnate causano 0 hard" vale
per i run misurati su TUTTE le famiglie hard (le uniche che fireano, H17/H29, sono unpinned-driven).

**Estendere canPin() NON e' giustificato** per i residui hard OSSERVATI (H17/H29, e H1/H3 = 0): il
validatore e' corretto, le pinnate non introducono infeasibility sui residui che compaiono nei run.
La diagnosi dei residui va altrove (LS compaction per H17, room-phase per H29), non sul pinning.
(H2/H7/H11 non ricomputati dallo script, ma 0 hard sui run misurati.)

## Caveat onesto (promoted pin)

Tutti gli export misurati mostrano `promoted=0` (le 2882-3090 pinnate sono TUTTE authoritative). Quindi
il rischio ex-ante ("i PROMOTED pin sfuggono al gate canPin") **non e' testabile su questi export**:
non ci sono promoted pin da misurare. Il verdetto "pinnate causano 0 hard" copre le AUTHORITATIVE
(validated); le PROMOTED restano un caso aperto (se compaiono in run con promotion attiva e
source=input, andrebbero ri-misurati). Nota: H17/H29 esentano le pinnate per costruzione (anche le
promoted, che sono `pinned=true`), quindi anche le promoted sarebbero 0-violanti su H17/H29; rimarrebbe
solo il rischio H1/H2/H3 (conflict) per promoted, che qui e' 0.
